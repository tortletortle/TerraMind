# V0.4 Function Calling boundary

## Purpose
The model is allowed to propose scene edits, not to directly mutate the Three.js scene or execute code. The expected flow is:

\`user request → model tool call → validateToolProposal → preview → user confirmation → commitPlan\`

## Tool
\`llm-contract.mjs\` exports \`TERRAMIND_FUNCTION\` (\`propose_scene_operations\`). The proposal is limited to:

- \`create\`: create one supported primitive entity.
- \`update\`: modify an existing entity by stable scene ID.
- \`delete\`: delete an existing entity by stable scene ID.

No JavaScript, HTML, URL, shader source, arbitrary component type or arbitrary property is accepted as an operation.

## Validation and commit
\`validateToolProposal\` checks operation shape, rejects undeclared fields, removes nullable placeholder values used by strict tool schemas, and validates the resulting operations against a cloned \`SceneDocument\`. It returns a preview plan and does not mutate the live scene.

\`commitPlan\` checks that the live scene snapshot still matches the snapshot used to create the plan. If another edit has happened, the plan is stale and must be regenerated.

## Security boundary
- Do not place provider API keys in \`index.html\`, \`view.mjs\`, browser storage or committed source files.
- The future provider adapter belongs on a server-side boundary and should read credentials from environment secrets.
- Treat model output as untrusted structured data.
- Never use \`eval\`, \`Function\`, dynamic imports or generated scripts to apply a model response.
- Keep explicit user confirmation before any model-proposed scene mutation.

## Current status
The tool schema and deterministic validator are implemented and tested. There is no live LLM request, provider SDK, API endpoint, credential handling or browser-to-server transport in V0.4. This is an intentional separation: the scene-operation contract is tested before a provider is connected.
