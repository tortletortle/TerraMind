# TerraMind V0.5 — LLM gateway

## Scope
V0.5 connects the existing scene-operation contract to a real OpenAI-compatible model endpoint. The model receives the user's command, structured entity metadata, rotation-aware conservative world AABBs for entities and composite groups, the selected entity, bounded conversation context, and up to eight recent messages (normally four user/assistant exchanges). Cylinder/cone bounds are conservative primitive-box bounds, not exact curved-surface bounds. It may return one propose_scene_operations function call or a text clarification. The server validates every proposal through validateToolProposal; the browser still displays a preview and requires explicit confirmation before commitPlan changes the scene.

This is structured scene understanding, not visual scene understanding: the model currently receives entity names, types, transforms, materials, colors and group metadata, not a screenshot or rendered pixels.

## Supported API modes

### Chat Completions
- TERRAMIND_API_MODE=chat_completions
- Default endpoint: https://api.openai.com/v1/chat/completions
- Function tool shape: type=function with a nested function object containing name, description, parameters and strict.
- Function calls are read from choices[0].message.tool_calls.

### Responses
- TERRAMIND_API_MODE=responses
- Default endpoint: https://api.openai.com/v1/responses
- Function tools use top-level type, name, description, parameters and strict fields.
- Function calls are read from output items with type=function_call.

TERRAMIND_API_URL can override the exact endpoint. The endpoint must be HTTPS, except for loopback development services. Both modes use bearer-token authentication. Azure-style api-key header authentication and provider-specific request formats are not implemented in this slice.

OpenAI's current function-calling documentation distinguishes the two request shapes and notes that some newer model families require the Responses API for tool calling. In particular, the documentation currently identifies GPT-6 Astra and GPT-6.1 Sol as Responses-only for tool calling; select responses mode for those models and verify the exact model's API compatibility before configuring a provider.

## Configuration
Copy .env.example to .env, then set:
- TERRAMIND_API_KEY: provider API key. Never commit this value.
- TERRAMIND_MODEL: exact model identifier enabled by the provider account.
- TERRAMIND_API_MODE: chat_completions or responses.
- TERRAMIND_API_URL: optional exact endpoint override.
- TERRAMIND_STRICT_TOOLS=0: opt out only if the selected provider does not support strict function calling. Server-side validation remains mandatory.
- TERRAMIND_TIMEOUT_MS: 1,000–120,000 ms; default 45,000.

Start with Node.js 22:

~~~bash
node --env-file=.env server.mjs
~~~

Open http://127.0.0.1:8000. If no API key/model is configured, the server still starts and the browser falls back to the constrained local rule planner.

## Request flow
1. Browser sends the current scene snapshot, command, selected entity, bounded context and recent turns to POST /api/plan.
2. Server restores the scene snapshot with SceneDocument.restore; invalid snapshots are rejected.
3. Provider adapter constructs a Chat Completions or Responses request and supplies the propose_scene_operations tool.
4. The model may ask a clarification in ordinary text, or return one function call. Multiple calls, wrong tool names, malformed JSON and truncated output are rejected.
5. validateToolProposal checks the operation allowlist and validates the entire batch against a cloned scene. It does not mutate the live browser scene.
6. The browser shows a preview. commitPlan checks that the scene snapshot is unchanged and only then applies the operations after the user confirms.

## Security and resource boundaries
- Provider credentials exist only in the Node process environment. They are not returned by /api/health, sent to the browser, or written to browser storage.
- The server binds only to loopback (127.0.0.1 by default). It refuses non-loopback binding. Public deployment is not supported until authentication, TLS termination, per-user authorization and deployment-specific rate limits are implemented.
- The API requires same-origin browser requests, JSON content type, a 256 KB request-body cap, a 200 KB scene snapshot cap, a 300-entity scene cap and a 20-request/minute in-memory limit per client address.
- Static serving uses an explicit allowlist; server code, .env, tests and documentation are not served as web assets.
- Provider output is untrusted. It can only propose the three allowed operation types; SceneDocument validation rejects invalid geometry, values, colors, scales and IDs.
- No model-generated JavaScript, HTML, shader, URL or shell command is executed.
- Responses mode sends store=false. Chat Completions retention behavior is governed by the selected provider and account settings; do not assume identical storage policies across providers.
- Scene metadata and up to eight recent messages (normally four user/assistant exchanges) are sent to the configured model provider. Do not use the AI mode with sensitive scene names or data unless the provider's data-handling terms are acceptable.

## Tests
~~~bash
node --check server.mjs
node --check llm-provider.mjs
node test-llm-provider.mjs
node test-server.mjs
~~~

These tests use mocked provider responses. They validate request construction, both API response formats, tool-call parsing, proposal validation, error redaction, local HTTP routing, origin checks and missing-credential behavior. They do not prove a real provider account, model entitlement, API key, billing configuration or network path works; a real API smoke test is still required.
